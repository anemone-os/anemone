# TLB 优化研究

## 研究问题

软件构建会频繁创建线程、分配用户页并修改页表。页表变化后，内核需要在必要时清除 TLB 中的旧地址转换结果。早期实现不区分变化类型，一律立即、逐页刷新，行为正确但比较保守。研究分别处理两类开销：大范围内核映射产生的重复刷新，以及新增用户映射后并非总有必要的立即刷新。

## 合并内核栈的大范围刷新

`pthread.createjoin_minimal1` 的路径分解显示，512 KiB 内核栈包含 128 个映射页和一个保护页。一次完整的创建与回收会执行 257 次逐页本地刷新；2506 个线程生命周期形成 5,012 次范围操作，累计涉及 644,042 个页面。

对照实验保持栈大小、保护页和页表项工作量不变，只将大范围逐页刷新替换为一次本地全地址空间刷新。正式实现随后在架构分页层统一选择方式：小范围仍逐页处理，大范围由 Kconfig 阈值选择一次完整刷新。关闭性能统计后，RV64 定向负载中的两组相邻比较分别改善 16.7% 和 14.8%。统计窗口记录到 644,042 个范围页面、5,012 次完整刷新和 0 次逐页刷新，证明收益来自刷新方式变化，而不是缩小内核栈。

公开身份：正式实现 `0e68c9736b0fa6f95374127308dd1790e4f559c3`；实验环境为 RV64、SMP=1、QEMU release；负载为串行创建并回收 2500 个线程，重复五次。LA64 的对应大范围策略由 `b267d2bc6ce89194da8502700d42dd6165542432` 实现，但上述百分比只来自 RV64 实验。

## 减少新增用户页映射后的冗余刷新

第二项研究区分第一次新增页表项、页表项未变化、放宽权限，以及替换或收紧权限。只有“真实用户缺页、第一次新增映射、处理后返回用户态”可以省去本次立即刷新；替换映射、收紧权限、内核主动触发缺页、futex 和用户内存访问恢复仍然同步刷新。如果硬件缓存了无效或受限的转换并使同一指令再次异常，第二次处理不再属于新增映射，内核会立即刷新后重试。

固定代码和配置后，RV64/QEMU TCG Cargo 实验严格按 `A1 -> B1 -> B2 -> A2` 执行四次独立启动交错对照。同一次启动内的 Cargo 数据中，原版本为 5.34/6.14 s，优化版本为 3.78/3.92 s，中位数从 5.740 s 降至 3.850 s，改善 32.93%。统计显示，第一次新增映射占真实用户缺页的 97% 以上，并与省去立即刷新的次数一一对应。

该数字证明优化方向在 QEMU TCG 下有效，不等同于最终 BuildStorm 增益。正式内核由 `777b031a` 实现本 CPU 的刷新策略，`503d6522` 保证替换或删除映射时先等待其它 CPU 确认、再释放资源，`23a9172496d4cdf662444f598b1581e296b3ba95` 则记录每个用户地址空间实际运行过的 CPU，只向可能持有旧转换的 CPU 发送请求。后两项用于保证多核正确性和可扩展性，本报告不为它们单独声明未经测量的性能数字。

## 结论边界

- 内核栈数据来自 pthread 定向负载；用户缺页数据来自 Cargo 工作负载，两者不可相加。
- 关闭性能统计后的时间承担性能结论；开启统计时的计数只用于解释机制。
- RV64/QEMU/SMP=1 的百分比不外推为 LA64、八核或实体硬件的固定收益。
- 正式实现没有通过缩小内核栈、减少构建工作或放宽正确性检查获得加速。
