# 复用已解析的目录项

## 研究问题

Cargo 和 `rustc` 会重复访问大量源码、元数据和构建产物。Anemone 的 VFS 使用目录项（dentry）表示一次路径解析结果，但旧实现只保存弱引用；最后一个使用者释放引用后，下一次访问相同路径必须重新查询文件系统。

研究阶段先用有界队列临时保留目录项。在固定 Cargo 负载中，文件系统查询从 4,418 次降至 638 次，下降 85.56%；VFS 直接命中与文件系统查询的总量仍为 13,520，说明路径访问没有被删除，只是更多请求复用了已有结果。这个实验只用于确认优化方向，临时队列没有直接进入正式内核。

## 实现方式

正式实现 `4214f95c9b04689f8bd922aec4e9a31ec8ac2c96` 为每个文件系统实例建立有界的已解析目录项保留区：

- 目前只对 ext4 启用，正式配置默认最多保留 1024 项；
- 文件系统仍然决定目录中实际存在什么，VFS 只延长已经成功解析的目录项生命周期；
- 查询和创建记录对应的命名空间代次，成功的 unlink、rmdir 和 rename 会推进代次并清除相关项；
- 容量不足时只是不再保留，不会改变系统调用结果；
- 删除记录时先在锁内摘除引用，再到锁外释放；最后一个挂载视图卸载时清空全部记录。

这套设计没有把研究用的 16K 队列、临时统计项或额外文件系统回调带入正式内核，也没有增加负目录项缓存、全局目录项缓存或用户可见的缓存承诺。

## 正式版本对照结果

对照使用原版本 `825d4cc6541687ee750131ad2161d58505ba27d4` 和优化版本 `44abcddac727c8f74b953bd8ff41f37de3bfd954`；两者之间的源码差异由正式提交 `4214f95c9b04689f8bd922aec4e9a31ec8ac2c96` 交付。实验在 RV64、SMP=1、8 GiB、QEMU release 模式中执行 `A1 -> B1 -> B2 -> A2` 四次独立启动交错对照。每次启动预热后，在关闭性能统计的情况下运行七次清理构建目录后的 Cargo 编译，并比较每次启动的中位数：

| 状态 | 两次启动的中位数 | 总体趋势中位数 |
| --- | ---: | ---: |
| 原版本 | 4.22 / 3.92 s | 4.070 s |
| 优化版本 | 3.72 / 3.73 s | 3.725 s |

: 目录项复用优化的四次启动对照结果

Cargo 改善 8.48%，优化版本的两次启动中位数都低于原版本区间。直接运行 `rustc` 时，耗时从 2.810 s 降至 2.495 s，同向改善 11.21%。四次启动都通过完整 KUnit、构建产物哈希、性能统计恢复和数据同步检查，并由内核正常关机。

该结果说明默认容量 1024 在这里记录的负载中保留了研究收益。具体容量、替换方式和内存压力下的行为属于实现选择，不构成固定性能保证。
