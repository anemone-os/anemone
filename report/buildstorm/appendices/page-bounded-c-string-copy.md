# 按页批量读取用户字符串

## 研究问题

文件路径、可执行文件路径等系统调用参数需要从用户空间读取以 NUL 结尾的 C 字符串。原实现逐字节检查并读取，能够准确处理非法地址、跨页和长度边界，但在构建负载中会产生大量重复检查和循环开销。`argv`/`envp` 字符串数组不属于本项优化范围。

参数实验比较了 64、128、256 和 512 字节四种上限。一次定向负载包含 2,399 次调用和 162,542 个有效字节；原路径近似逐字节处理，256 与 512 两种方案都只需要 2,405 次页内批量读取。512 不会进一步减少读取次数，只会读取更多无用字节，因此选择 256。

## 实现方式

正式实现 `1d0a525f9baceeb1b08662b473b52a6a831fd9b2` 每次请求：

```text
min(256, 到页尾的字节数, 到用户地址上界的字节数, 剩余长度上限)
```

批量读取始终不跨越用户页、用户地址上界或 `MAX_BYTES + 1`。如果读取中途遇到不可访问地址，内核会先检查已经复制的前缀：前缀中已有 NUL 时仍然成功，否则返回原有错误。第 `MAX_BYTES + 1` 个可读字节仍为非零时，继续返回原有的长度错误。直接字符串和路径使用批量读取，字符串数组继续使用原来的逐元素路径。

256 字节上限通过 Kconfig 配置，内核在编译时保证它位于 `1..=PAGE_SIZE`。

## 正式版本对照结果

原版本与正式优化版本在 RV64、SMP=1、8 GiB、QEMU release 模式中执行 `A1 -> B1 -> B2 -> A2` 四次独立启动交错对照。每次有效启动都在关闭性能统计后运行七次清理构建目录后的 Cargo 编译：

| 状态 | 两次启动的中位数 | 总体趋势中位数 |
| --- | ---: | ---: |
| 原版本 | 3.84 / 3.70 s | 3.770 s |
| 优化版本 | 3.71 / 3.55 s | 3.630 s |

: 用户字符串批量读取优化的四次启动对照结果

两组相邻比较分别改善 3.39% 和 4.05%，总体趋势改善 3.71%。直接运行 `rustc` 时，两组分别改善 7.22% 和 5.68%。所有有效启动都通过 KUnit、构建产物、性能统计恢复和数据同步检查，并由内核正常关机。正式计时前曾有一次尝试未通过正确性检查，因此没有产生性能样本，也没有进入统计。

该实现保持系统调用 ABI、错误码、NUL、跨页异常、UTF-8 和最大长度处理不变。3.71% 只适用于这里记录的 RV64/QEMU Cargo 配置，不能当作可与其它优化相加的 BuildStorm 增益。
